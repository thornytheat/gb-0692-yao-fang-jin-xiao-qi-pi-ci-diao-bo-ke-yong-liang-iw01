# 调拨收发对账（运行期）

合规调拨单获批后由仓库整批发货，门店常分多次收货。本子系统按**单据级事件流**重算每张调拨单的在途、已收、短少与可再分配量，给出可发布、可复算、可留痕的对账结论。与 M1–M7 的计划期流水线相互独立：计划期回答"该发什么"，本模块回答"发出后对上了没有"。

## 一、守恒口径（每张调拨单恒成立）

```
批准量 = 原发待发 + 已收 + 在途 + 净短少 + 可再分配
```

- **原发待发**：已获批但仓库尚未整批发出的数量。仓库整批发出前库存不释放，别家拿不到。
- **已收（=门店库存）**：只统计门店回执确认实收的数量。**未收清的在途量不计门店库存，也不另许给别家。**
- **在途**：已发出但门店既未回执、也未做短少认定的数量（含补发在途）。
- **净短少**：累计认定短少（毛额）扣除已被补收回的、晚到补齐的、补发已在途的部分。
- **可再分配**：晚到且该门店不再需要、退回中央仓可重新分配的数量。

派生恒等关系：`净短少 = 认定短少(毛) − 补发已收 − 晚到已补齐 − 补发在途`。

## 二、关键业务规则

1. **整批发货**：原发批次数量必须等于批准量；原发只能一次，不可重复原发。
2. **短少补发接回原单**：补发是同一调拨单下 `kind=reship` 的新发货批次，不新开单；补发量不得超过"已认定但尚未补发"的短少量。
3. **晚到收货不重复冲减**：短少认定后又到达的货，先冲减对应净短少（缺口已消失），货物本身转**可再分配**而不是计该门店库存；同一回执号重复提交被拒绝。
4. **收货先回补在途**：一次收货中，落在在途额度内的部分计实收，超出部分按晚到处理。
5. **结清即冻结**：`order_closed` 后该单不再受理任何收发事件。

## 三、单据状态机（看板"卡在哪一步 / 能否继续发放"）

| 状态 | 含义 | 可继续发放 |
|---|---|---|
| 待发货 | 已获批，仓库未整批发货 | 否 |
| 部分收货在途 | 原批次仍有在途，等回执或短少认定 | 是 |
| 短少待补发 | 已认定短少，可接原单补发 | 是 |
| 补发在途 | 补发批次已发、门店未收 | 是 |
| 待短少认定/结清 | 在途清空但仍有净短少 | 是 |
| 可结清 | 批准量已收齐（晚到转可再分配） | 否 |
| 已结清 | 单据关闭 | 否 |

## 四、事件类型

`order_approved`、`shipment_sent`（original/reship）、`receipt_recorded`、`shortage_claimed`、`order_closed`。每条事件须有唯一 `event_id`、`occurred_at`（ISO8601）、`order_no`。非法事件返回 422 并带 `RECON_*` 原因码。

## 五、版本化、幂等与留痕

- 事件表**只增不改不删**，原始调拨单与收货回执报文（`raw`）永久留存。
- 一批事件在单事务内校验并落库：**任一条非法则整批回滚，上一版对账结论原样保留**。
- 同批次重跑（事件均已入账）：标记 `reused`，不重复写事件、不新增加扣减，结论与上一版逐字段相同。
- 增量合法事件产出新版本；版本号在每个批次内从 1 独立递增，历史版本均可追溯。
- 状态由事件流纯函数重算（`app/recon/engine.py::replay`），确定性、可离线复算。

## 六、接口与页面

- `POST /api/recon/events`：body `{batch_id?, events:[...]}`，省略 batch_id 时由内容派生幂等批次。
- `POST /api/recon/demo`：装载/重跑内置演示批次（含分批收货、短少补发、晚到转出、在途未清、待发货、补发在途六类单）。
- `GET /api/recon/batches`：批次列表；`GET /api/recon/batches/<id>`：当前对账结论；`.../ledger`：事件凭证与版本历史。
- 页面 `/recon`：看板展示每张单的状态、能否继续发放、守恒是否相符及批次凭证；M6 页面提供入口。
- 账本使用独立 SQLite（环境变量 `RECON_DB`，默认 `data/recon.sqlite3`），与计划期 `runs.sqlite3` 分离。
